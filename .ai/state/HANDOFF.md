## Last session — 2026-07-11 (Claude Code / Sonnet 5) — email + username + password accounts, replacing passkey-first as the primary sign-in surface

- **What changed and why:** Owner feedback on the G6 passkey-first sign-in (previous entry below): too confusing, wanted "dead simple" account creation, specifically email + username + password. Nothing from G6 was removed; the passkey and magic-link/code endpoints, tables, and client helpers are all still fully functional. Only the *featured* sign-in surface changed.
  - **Worker:** new `worker/src/lib/password.ts` (PBKDF2-SHA256 via `crypto.subtle`, 100,000 iterations, random 16-byte salt, both stored as hex; `hashPassword`, `verifyPassword` with a constant-time compare, and `dummyVerify` for timing-safe "no such account" handling). New `worker/src/routes/auth.ts` endpoints `POST /register` `{email, username, password}` and `POST /login` `{identifier, password}`, both CSRF-header-gated the same way `/code/verify` and passkey `login-verify` already are (unauthenticated by definition, since they're how a session gets created). `register` validates email format, username (`/^[a-z0-9_]{3,20}$/i`), password length (>=8), pre-checks username/email uniqueness, then either INSERTs a new user or, if an existing *passwordless* account already owns that email (created via magic link, Google, or a bare passkey-eligible row), UPDATEs that same row instead of erroring, same id, one more door into the same account. A `try/catch` around the write itself maps a UNIQUE-constraint violation (by column name in the D1 error message) back to the right `409 {username_taken|email_taken}`, closing the race window between the pre-check and two near-simultaneous registrations for the same name. `login` looks up by `email = ? OR username = ?` (both columns are `COLLATE NOCASE`, so this is inherently case-insensitive with no explicit `COLLATE` needed at the query site) and returns the exact same `401 {error:'invalid_credentials'}` for every failure mode, bad input, unknown identifier, an account with no password set, or a wrong password, with a dummy PBKDF2 derive on the no-real-hash-to-check paths so none of those cases are distinguishable by response time either. `worker/src/lib/crypto.ts` gained `bufToHex`/`hexToBuf` (factored out of the existing `sha256Hex`, used by `password.ts`). `User`/`loadUser()`/`/me`/`/code/verify`/passkey `login-verify` all now carry `username` through to the client alongside the existing `email`/`displayName`.
  - **New D1 migration:** `worker/migrations/0003_password_auth.sql`, additive only: `users` gains `username TEXT COLLATE NOCASE`, `password_hash TEXT`, `password_salt TEXT`, `password_iterations INTEGER` (all nullable, so every existing row is untouched and keeps signing in exactly as before), plus `CREATE UNIQUE INDEX idx_users_username ON users(username) WHERE username IS NOT NULL`. SQLite's `ALTER TABLE ADD COLUMN` can't carry a `UNIQUE` constraint directly (confirmed against SQLite's own docs when the first attempt at this migration failed to apply locally), hence the separate partial index; see `.ai/memory/GOTCHAS.md`. Mirrored into `worker/src/lib/schema.ts`'s `INIT_SCHEMA` bootstrap. **Applied to LOCAL D1 only** (`--local`, for the runtime testing below); **not applied to remote/production**, deliberately left for the user, same reasoning as G6 below and detailed in "Branch" below.

The old passkey-sign-in button and the magic-link/6-digit-code form are gone from this surface entirely (per the task: "stop featuring them in the UI"), along with their now-dead CSS (`.account-passkey-signin`, `.account-divider`, removed from `base.css`). `PasskeyManager` (add/list/remove passkeys) is untouched in place and function, it already only ever rendered inside the signed-in `SignedIn` branch, so "passkeys live quietly in account settings only" was already true structurally; only its nudge copy changed (stopped referencing "an email code" as the alternative, since email code is no longer what a reader would compare it against). `SignedIn` now shows both `Email` and `Username` as explicit `.settings-row`s (reusing the existing row pattern instead of inventing a new one) alongside the existing Sign out button. `app/src/lib/api.ts` gained `register`/`login` calls, a shared `AuthUser` type (used by `Me`, `verifyCode`, `passkeyLoginVerify`, and the `user` signal in `app/src/lib/state.ts`, so every sign-in path now returns/consumes the same shape), and `ApiError` gained a `.slug` field (best-effort parse of the server's `{error:"<slug>"}` body, matching `docs/api.md`'s documented error-shape contract, no new response shape invented) so the UI can show distinct copy per registration failure while the sign-in form deliberately ignores the slug and always shows one generic sentence.
